# tg-spam Development Guidelines

## Build & Test Commands
- Build: `go build -o tg-spam ./app`
- Run tests: `go test -race ./...`
- Run single test: `go test -v -race ./path/to/package -run TestName`
- Lint: `golangci-lint run`
- Coverage report: `go test -race -coverprofile=coverage.out ./... && go tool cover -func=coverage.out`

## Important Workflow Notes
- Always run tests and linter before committing
- For linter use `golangci-lint run`
- Run tests and linter after making significant changes to verify functionality
- Go version: 1.25+
- Don't add "Generated with Claude Code" or "Co-Authored-By: Claude" to commit messages or PRs
- Do not include "Test plan" sections in PR descriptions
- Do not add comments that describe changes, progress, or historical modifications. Avoid comments like "new function," "added test," "now we changed this," or "previously used X, now using Y." Comments should only describe the current state and purpose of the code, not its history or evolution.
- Use `go:generate` for generating mocks, never modify generated files manually. Mocks are generated with `moq` and stored in the `mocks` package.
- After important functionality added, update README.md accordingly
- When adding new CLI parameters or environment variables, update BOTH:
  1. The "All Application Options" section in README.md (should match `--help` output exactly)
  2. The appropriate descriptive section in README.md (e.g., spam detection modules, OpenAI integration, etc.)
- When adding a new configurable parameter (CLI flag, env var, or any user-tunable knob), wire it through ALL of these layers — missing any one leaves the feature partially broken:
  1. **CLI/env definition**: `app/main.go` (flag + env var) and `app/settings.go` `optToSettings` mapping (CLI → Settings)
  2. **DB-backed config**: `app/config/settings.go` — add to the typed `Settings` struct with `json`/`yaml`/`db` tags. If `0`/empty must survive merges as a meaningful "disabled" value, add the dotted path to `zeroAwarePaths`. Add startup validation if needed.
  3. **Web settings UI**: `app/webapi/assets/settings.html` — add the form input (edit panel) AND the read-only display row. `app/webapi/config.go` — parse the new form field exactly like an existing analogous field (look for the closest sibling: int → `reportAutoBanThreshold`, duration → `reactionsWindow`, bool → existing checkboxes).
  4. **e2e UI test**: `e2e-ui/e2e_test.go` — add to the settings round-trip test so the form field is exercised.
  5. **Docs**: README.md (both options-table and descriptive section, per the rule above).
- When merging master changes to an active branch, make sure both branches are pulled and up to date first
- Don't add "Test plan" section to PRs

## Spam Detection Architecture

### Quoted/Reply-to Text Handling
- When checking messages for spam, quoted text is concatenated with the main message text
- This catches spammers who quote spam content from external channels
- `Quote` (from Telegram's TextQuote) takes precedence over `ReplyTo.Text`
- The concatenation uses newline separator: `msg.Text + "\n" + msg.Quote`
- Empty quote/reply-to text is ignored (no extra newline added)
- All three paths apply the same Quote concatenation: auto-detection (`app/bot/spam.go:OnMessage`), admin `/spam` (`app/events/admin.go:directReport`), and user `/report` (`app/events/reports.go:DirectUserReport`)
- Quote concatenation is placed AFTER the transform fallback block so image-only messages with quotes get both caption text and quote text
- Exception: `bot.OnMessage` also records the appended quote/reply text in `spamcheck.Request.Quote`. The prohibited-language hard check reads `req.AuthoredText()` (which strips the trailing `"\n"+Quote` from `Msg`) instead of `req.Msg`, so quoted foreign-script content the user did not author cannot trigger its LLM-unvetoable permanent ban; all other (soft, vetoable) content checks still see the full concatenated `req.Msg`
- The duplicate detector (`lib/tgspam/duplicate.go:check`) hashes the full `req.Msg` but skips a message whose `req.AuthoredText()` is empty. Otherwise every caption-less item of an album posted as a reply has `Msg == "\n"+parent`, all hash the same, and the sender is banned on item `threshold`. The key stays `req.Msg`, not `AuthoredText()`: keying on authored text alone would make identical short replies ("thanks") to different parents collide, and this check bans approved users. Accepted cost: caption-less media repeatedly quoting the same text is not counted. On that skip `forgetMessage` drops the entry already stored for the message ID, because edits are re-run as new messages (`listener.go`, `EditedMessage` branch) and a caption edited away would otherwise keep counting. That covers only edits the intake guard admits (photo, video, video note, forward, external reply, and a document, contact or audio admitted by its meta check). A text-less edit the guard drops (a file or GIF, contact or audio with its meta check off) never reaches `Detector.Check`, so the guard itself calls `Bot.ForgetMessage` → `SpamFilter.ForgetMessage` (resolves `SenderChat.ID` over `From.ID`, like `OnMessage`) → `Detector.ForgetMessage` before returning, and only when `update.Message.EditDate != 0`. It clears duplicate history and nothing else: no locator write, no checks. An album with the same caption on every item still counts each item; `media_group_id` is not read anywhere

### Rich Message (Article) Handling
- Telegram's client "Article" compose type (attach menu → Article) arrives via the Bot API as `Message.rich_message` (added in Bot API 10.2; requires `OvyFlash/telegram-bot-api` ≥ the 2026-07 / 10.2 revision). Older clients and the Bot API render it as "This message is not supported in your version of Telegram". Spammers used it to hide the pitch (e.g. free-VPN ads) out of `msg.Text` so no content check fired
- `transform` (`app/events/events.go`) flattens `rich_message` into `message.Text` right after the caption block, mirroring the caption pattern (set if `Text` empty, else append with `"\n"`). This routes the content through the entire existing pipeline unchanged — stopwords/classifier/LLM/prohibited-langs plus the locator (so duplicate detection works). No new config, not gated: it just feeds previously-invisible text to the same checks
- The library types `RichBlock` and `RichText` are bare `any` with no custom unmarshaler, so an incoming `rich_message` decodes as generic `map[string]interface{}`/`[]interface{}`, NOT the concrete `RichBlock*`/`RichText*` structs (those are for outgoing construction). A nested recursive closure walks the generic tree and collects non-empty string leaves under text-bearing keys (`text`, `caption`, `credit`, `summary`, `expression`, `alternative_text`); URLs, `type`, and list-item marker labels are intentionally dropped. Maps are visited in sorted-key order for deterministic output; block/span arrays keep document order
- Because the flattened text is non-empty, the message survives the empty-text intake guard in `procEvents` (`listener.go`) automatically; forwarded articles (`forward_origin` set) also work. A rich message with no extractable text (media-only) still yields empty `Text` and is dropped by that guard — accepted, since there is no content to check

### Checklist and Poll Handling
- Checklist messages (`Message.checklist`) and polls (`Message.poll`) carry their text outside `msg.Text`. Spammers used checklists on radio-t (title plus tasks with the pitch and a `t.me` link), and with empty `Text` the `listener.go` empty-text guard dropped them before any check or locator write
- `transform` appends caption, rich message, checklist and poll text in that order through one local `addText` closure (set if `Text` empty, else append with `"\n"`). `checklistText` gives title then task texts; `pollText` gives question, description, option texts, then explanation; both skip empty strings
- Only the text is copied, not `title_entities`/`text_entities`/`question_entities`, so entity-based meta data gains nothing; `LinksCheck` still counts `http(s)://` in the text when `Meta.Links` is 0
- Not covered: `ExternalReplyInfo.Checklist`/`.Poll` (another author's content, must not become authored text for prohibited-langs), a reply's `ReplyTo.Text` when the parent is a checklist or poll, and checklist task-added/done service messages
- Accepted limit: `ChecklistTask` has no author field, so tasks other members add to a checklist with `others_can_add_tasks` are judged as the sender's own text when a later edit is re-checked (edits run as new messages), including by the unvetoable prohibited-langs check. The approval gate still applies except in paranoid or check-all mode. Skipping collaborative tasks is not the fix: a spammer can set that flag to hide the pitch again
- Admin-chat forwards (`admin.go` `MsgHandler` and `msgHandlerFallback`) run the diagnostic `OnMessage` on `msgTxt`, the transform fallback text, so a forwarded caption-only, checklist or poll message reports checks on its real content

### CAS Token
- api.cas.chat answers every request without a key with 401 "API key required" (since 2026-10-25). `--cas.token` / `CAS_TOKEN` (Settings.CAS.Token) carries the Combot API key; `Detector.Check` runs CAS only when both `CasAPI` and `CasToken` are set, and `makeDetector` logs one `[WARN]` when the URL is set without a token
- The token goes in the `Authorization: Bearer` header, never the `api_key` query parameter: `isCasSpam` puts the request URL into `Details` and log lines. 401 and 403 return the wrapped `errCasAuth` sentinel, which `repeater.Do` treats as terminal, so a rejected token costs one request; 429 and other non-200 statuses are still retried
- `IsCASEnabled()` stays URL-only. It drives the web form's `casEnabled` checkbox, and unchecking it clears `CAS.API` (`app/webapi/config.go`). A token-aware predicate would render the box unchecked for every token-less install, so any unrelated dashboard save would clear the URL, and dashboard saves write the empty URL to the DB. The read-only row shows `true (inactive, no token)` instead
- It is a credential wired like `Jev.Token`: `FieldCASToken` in `crypt.go` `sensitiveFieldAccessors`, `applyCLIOverrides` `cliCredentials`, `collectMaskedSecrets`, and the blanking list in `getSettingsHandler` (`app/webapi/webapi.go`), which is the sink easiest to miss since GET /settings otherwise returns every token in its JSON. The form never reads it
- `api.cas.chat/export.csv` returns 404 "CSV exports are not supported anymore"; only `/check` remains

### External Reply Detection
- `--meta.external-reply` / `META_EXTERNAL_REPLY` (Settings.Meta.ExternalReply) is an opt-in meta check that flags any message replying to a message from another chat (Telegram's `external_reply`, distinct from an in-chat `reply_to_message`). Disabled by default. Targets the "reply to an external scam channel + short fake-testimonial comment" pattern (observed: replies to a Beeline-scam channel with `text`="Пришло быстро!" and a bold `quote`="Написать менеджеру: @Beeline"), where the classifier/similarity/LLM see only the tiny comment and clear it
- Mirrors `ForwardedCheck` exactly: blunt (any external reply → spam), no gating beyond the on/off toggle. It is a distinct check from `forward` because `external_reply` is a reply, not a forward — `msg.ForwardOrigin` is nil for these, so the `forward` check reports "not a forwarded message" and never fires on them
- Wiring (standard meta-check path): `msg.ExternalReply != nil` → `bot.Message.WithExternalReply` (transform, `app/events/events.go`) → `spamcheck.Request.Meta.HasExternalReply` (`bot.OnMessage`) → `ExternalReplyCheck()` (`lib/tgspam/metachecks.go`, returns `external-reply` spam/`external reply`). Gated in `app/main.go` by `settings.Meta.ExternalReply`; part of the `IsMetaEnabled()` aggregate; NOT in `zeroAwarePaths` (a plain opt-in bool, default false). Also exposed to Lua plugins as `req.meta.has_external_reply` (`lib/tgspam/plugin/checker.go`), like every other `Has*` meta field
- `transform` only sets `WithExternalReply` for a genuinely cross-chat reply: `msg.ExternalReply != nil && (msg.ExternalReply.Chat == nil || msg.ExternalReply.Chat.ID != msg.Chat.ID)`. Telegram's `external_reply` also fires for a reply *across forum topics within the same chat*; without the chat-ID guard, a legitimate cross-topic reply in a forum supergroup would be flagged (and, when enabled, permanently banned). A hidden/inaccessible origin chat (`Chat == nil`) is treated as external. The observed Beeline spam has `external_reply.chat.id != msg.chat.id`, so it is still caught
- Bot API limitation: `ExternalReplyInfo` (`vendor/.../types.go`) has no text/caption field, so the referenced external post's body text is unavailable — only its origin/chat identity and media type. The check therefore keys purely on presence, not content. The quoted snippet a spammer selects still arrives separately via `msg.Quote` and is handled by the existing quote concatenation

### Channel Message Handling
- When a channel posts in a group, Telegram uses a shared fake user `Channel_Bot` (ID `136817688`) in `msg.From`
- The actual channel identity is in `msg.SenderChat` with unique ID and username
- `SenderChat.ID` is used for locator tracking (`AddMessage`, `AddSpam`), and for banning via `BanChatSenderChatConfig`
- `bot.OnMessage` sets `Response.ChannelID = msg.SenderChat.ID` when SenderChat is present
- Admin `/spam` command (`directReport`) detects `origMsg.SenderChat` and passes channel ID for ban and cleanup
- Anonymous admin posts (where `SenderChat.ID == group chat ID`) skip spam check entirely
- Linked channel (resolved via `ChatFullInfo.LinkedChatID` at startup) is treated as superuser for `/ban`, `/spam`, `/warn` commands
- An anonymous admin of the monitored group (`From` = `GroupAnonymousBot`, `SenderChat.ID == Chat.ID == l.chatID`) is also treated as superuser for `/ban`, `/spam`, `/warn`, via `isAnonymousGroupAdmin` in `fromSuper`. The check compares against `l.chatID`, never `msg.Chat.ID` alone or `isChatAllowed`: `fromSuper` is computed before any chat filter, and the super-command handlers always act on the primary chat, so an anonymous admin of any other group the bot is in (including `TestingIDs` chats and the admin chat) would otherwise ban, delete and train spam samples in the monitored group
- Linked channel messages also skip spam checking (same as anonymous admin posts)
- `isLinkedChannel(msg)` helper checks `l.linkedChannelID != 0 && msg.SenderChat != nil && msg.SenderChat.ID == l.linkedChannelID`
- `channelDisplayName` resolves display name from `*tbapi.Chat`: UserName > Title > `channel_<ID>`
- `ReportBan` uses `https://t.me/<username>` links for channels (not `tg://user` which doesn't resolve negative IDs); plain name+ID for channels without username
- Admin `/warn` command (`DirectWarnReport`) targets the channel display name instead of `@Channel_Bot`
- Admin notification text in `directReport` shows channel display name and channel ID instead of Channel_Bot identity
- `extractUsername` supports `tg://user` links, `t.me` channel links, plain channel name+ID, and `{id name...}` formats

### Report Command Routing
- `spam`, `/spam`, `report`, `/report` are equivalent for a non-superuser: all four are matched by `isReportCommand` (`app/events/listener.go`) and behave identically in every path. `/report@botname` is additionally accepted; there is no `/spam@botname` equivalent, deliberately (nothing autocompletes it, the bot never calls `SetMyCommands`)
- The same text from a superuser, the linked channel, or an anonymous admin of the monitored group never reaches `isReportCommand` — `procSuperReply` intercepts it earlier in the `Do` loop for ban + spam-sample training. Identical text, different handler, decided purely by sender privilege
- **`isReportCommand` has THREE consumers**, and this is the trap: `procUserReply` (files the report), the foreign-chat drop in `Do` (below), and the orphaned-command cleanup in `Do`, which deletes a matching message sent *without* a reply. Anything added to the predicate immediately becomes deletable as an orphaned command, in every chat the bot receives updates for, and that branch is NOT gated on `ReportConfig.Enabled` — unlike `procUserReply`, which suppresses the command when reporting is off
- The user-report dispatch requires `update.Message.SenderChat == nil`. Senders posting on behalf of a chat carry a pseudo-user in `From` that can never be an approved reporter, so without the guard `DirectUserReport` deletes their command message and files nothing. Anonymous admins of the monitored group divert earlier through `fromSuper`, so the guard is what covers "post as channel" `Channel_Bot` senders from a non-linked channel and anonymous admins of other chats
- A non-superuser report command sent as a reply in any chat other than `l.chatID` (other groups, `TestingIDs` chats, the admin chat) is dropped in `Do` before the user-report dispatch, whatever `ReportConfig.Enabled` and `SenderChat` are. `DirectUserReport` always acts on the monitored group (deletes the command by its ID there, stores the report with `primChatID`), so a foreign report would delete an unrelated message with the same ID and later ban or delete by foreign IDs. It is dropped, not passed to `procEvents`: in a testing chat the spam check would judge `command + "\n" + reported text` as the reporter's own message and could ban the reporter. Same reason `isAnonymousGroupAdmin` compares against `l.chatID`, never `isChatAllowed`
- `DirectUserReport` resolves the reported identity from `SenderChat` before `From`, including when `From` is nil. Posts made as the group itself or its linked channel are rejected; `IsAutomaticForward` also rejects linked-channel posts when the startup-resolved ID is missing or stale. Other channels are stored under their negative ID. `ReportedUserName` is `@username`, then the channel title with leading `@` characters stripped, then `channel_<id>` if the stripped title is empty. This reserves the `@` prefix for real usernames: those render as `t.me` links, while titles render as plain text with the ID. Report callbacks and auto-bans use `channelIDFromCallback` to select `BanChatSenderChat`; channels are banned even in soft-ban mode, and all three ban notification paths report that outcome

### ExtraDeleteIDs Feature
- `spamcheck.Response` includes `ExtraDeleteIDs []int` field for additional message IDs to delete when spam is detected
- Any spam checker can populate this field to request deletion of related messages
- Currently used by duplicate detector to delete all previous duplicates when threshold is reached
- The listener handles these deletions with rate limiting (35ms between deletions) to respect Telegram API limits
- Deletion errors are logged but don't fail the operation (messages might be already deleted or too old)
- Design principle: When a spammer is detected, aggressively clean up ALL their spam messages, not just the triggering one

### Warn Auto-Ban
- `/warn` admin command optionally records each warning to `warnings` table and bans the user when count within `warn.window` reaches `warn.threshold`
- Disabled by default (`warn.threshold=0`); enabling preserves the existing warn message + delete behavior and adds the count/ban path on top
- Threshold semantics match `Report.AutoBanThreshold`: `count >= threshold` triggers ban (so threshold=2 bans on the 2nd warn)
- Storage layer (`app/storage/warnings.go`) opportunistically prunes rows older than 1 year on each `Add`; the 1y cap is a storage bound, NOT the configured window — `CountWithin` enforces the window at query time
- Ban does NOT delete the warning rows: subsequent `/warn` on an already-banned user re-triggers the ban path. Telegram's `BanChatMemberConfig` is idempotent, so the repeat ban is a no-op API call but produces a fresh admin-chat notification (audit visibility for repeat offenders)
- Warn auto-ban does NOT update spam samples (`bot.UpdateSpam` is not called) — warnings reflect admin policy, not spam content
- `executeWarnBan` mirrors `executeAutoBan` for dry/training/soft-ban handling but does not share an abstraction (the two diverge on spam-sample updates and on `From` vs `SenderChat` resolution)
- Settings: only `Warn.Threshold` is in `zeroAwarePaths` (0=disabled, must survive merges); `Warn.Window` zero is invalid and rejected by startup validation

### Short Message Flood Detection
- `--max-short-msg-count` (Settings.MaxShortMsgCount) bans an unapproved user who accumulates too many short messages without graduating to approved status; closes the gap left by content-based checks for spammers probing with innocuous one-word messages
- Disabled by default (`MaxShortMsgCount=0`); incompatible with paranoid mode (paranoid forces `FirstMessageOnly=false` and `FirstMessagesCount=0` in `makeDetector`, which would silently disable this check). `Settings.Validate` (`app/config/settings.go`) rejects `MaxShortMsgCount > 0 && ParanoidMode`, and also `MaxShortMsgCount > 0 && MinMsgLen <= 1`: `isShortMsgFlood` bails on any message at least `MinMsgLen` runes long, so 0 exempts every message and 1 every non-empty one, leaving only caption-less media to count
- `Settings.MaxShortMsgCount` is in `zeroAwarePaths` (0=disabled must survive merges); validation rejects negative values
- Trigger formula: `excess := total - approvedCount; spam := excess >= MaxShortMsgCount` where `total` is `CountUserMessages` from the locator and `approvedCount` is the in-memory `approvedUsers[id].Count` (incremented only on long ham messages, see the block at `detector.go:386-400`)
- Stateless within the detector — no cache, no separate struct. The check is an internal method `(d *Detector) isShortMsgFlood(req)` (`lib/tgspam/detector.go:1059`) called inline in `Detector.Check` after the duplicate-detector branch and before the stop-word/emoji/metachecks block, gated by an outer guard so disabled mode does no work
- Dependency: `MessageCounter` interface (consumer-side, defined in `lib/tgspam/detector.go`) implemented by `app/storage/locator.go` via `CountUserMessages` and `UserMessageIDs`. Wired in `app/main.go` with `detector.WithMessageCounter(locator)` after the locator is constructed
- Count query uses index `idx_messages_gid_user_id_time` (locator.go:70 sqlite, :74 postgres) — pure index scan, gid-scoped per the listener's locator
- Locator TTL pruning is rare for actively-evaluated unapproved users (cleanup only kicks in when `total > minSize`); accepted as a known limitation
- On flag, the response carries `ExtraDeleteIDs` populated from `UserMessageIDs(ctx, userID, MaxShortMsgCount*2)` so the listener cleans up prior messages alongside the triggering one (same pattern as duplicate detector)
- Bypasses LLM consensus by design: returns `true, cr` immediately when flagged instead of letting the unified `spamDetected`/LLM-consensus flow evaluate. Rationale: short-message flood is a behavioral signal that does not depend on content, and an LLM looking at the latest single short message has no information that would justify overriding the count
- Edge cases (handled via fast-bail returns in `isShortMsgFlood`): empty `req.UserID`, `req.CheckOnly`, message length ≥ `MinMsgLen`, user already approved (`approvedCount >= FirstMessagesCount`), locator error (logged at WARN, falls through to normal checks)
- Channel `SenderChat` flow works transparently: `bot.OnMessage` already maps `checkUserID = msg.SenderChat.ID` and the locator stores under the same ID; anonymous admin and linked-channel posts skip `OnMessage` entirely (listener.go:419-422)
- Edits: locator keys by `hash(text)` with `INSERT OR REPLACE` — no-op edits do not increment count; content-changing edits create a new row (consistent with `duplicateDetector`). Exception: text-less messages key by `hash("chatID:userID:msgID")` (`locator.go:AddMessage`), because every empty text hashes to `sha256("")` and would collapse all caption-less media in a gid onto one row under `PRIMARY KEY (gid, hash)`. An edit of such a message keeps the same key, so the no-op-edit property holds
- Media-only messages (photo/video/document with no caption, GIFs included) therefore count toward `total`: they reach `AddMessage` with empty text (the intake guard in `procEvents` passes them on `msg.Image`/`WithVideo`/`WithVideoNote`/`WithForward`/`WithExternalReply`, and on `WithDocument` only when `AdmitDocuments` is set) and `isShortMsgFlood` treats length 0 as short. This is intentional — image-flood probing is a real spam pattern — but it means an unapproved user posting N caption-less photos accumulates N, not 1
- Training/dry/soft-ban: feature emits a normal spam result through the existing pipeline, so the listener's mode handling intercepts identically to other spam checks (no special-casing)
- Naturally-terse legitimate users carry a bounded false-positive risk during the evaluation window only; once the user crosses `FirstMessagesCount` they are approved and immune. Recommended baseline: `MaxShortMsgCount >= 3` with low `FirstMessagesCount` (1–2)

### Document Detection
- `--meta.document-only` / `META_DOCUMENT_ONLY` (Settings.Meta.DocumentsOnly — Go field stays plural, like `VideosOnly` behind `--meta.video-only`) flags a message carrying a document (file attachment) whose text is empty or shorter than `--min-msg-len`. Disabled by default. Mirrors `VideosCheck`/`AudioCheck`: `DocumentsCheck(minTextLen int)` in `lib/tgspam/metachecks.go`, gated in `makeDetector` by the setting, wired through `spamcheck.MetaData.HasDocument` (`bot.OnMessage`) and `bot.Message.WithDocument` (`transform`, `app/events/events.go`). Also exposed to Lua as `req.meta.has_document`. Web form field is `metaDocumentOnly`
- Unlike its siblings the check measures `req.AuthoredText()`, not `req.Msg`: `bot.OnMessage` appends quoted/reply-to text to `Msg`, so a caption-less file posted as a reply would otherwise arrive with a non-empty `Msg` written by someone else and clear the length gate (at the default `min-msg-len=50` a 49-rune parent suffices, the appended `"\n"` counting). Same reasoning as the prohibited-languages check, but here it changes an ordinary soft verdict, not a hard ban
- Forwards are not special-cased. Telegram delivers a forwarded document as an ordinary message with `document` set and the *original* caption in `caption`, and `transform` already folds `caption` into `message.Text` before this check runs. A forwarded file with a long original caption looks identical to a directly posted file with a long caption — both pass. The missing text is the signal, not the forwarding; an operator who wants to act on forwarding as such already has `--meta.forward`
- GIFs count as documents. Telegram sets `message.document` for animations too (`vendor/github.com/OvyFlash/telegram-bot-api/types.go`, the `Animation` field doc: "For backward compatibility, when this field is set, the document field will also be set"). The check does not exclude `msg.Animation`, so a GIF whose caption is shorter than `--min-msg-len` — nearly every GIF — is flagged when the check is on. Deliberate strictness, not an oversight
- The intake guard in `procEvents` (`listener.go`) admits a text-less document only when `TelegramListener.AdmitDocuments` is set (wired from `settings.Meta.DocumentsOnly` in `app/main.go`), so with the check off a directly posted one is dropped before `Locator.AddMessage` as before. Not so for a forwarded file or one attached to a cross-chat reply: `WithForward`/`WithExternalReply` short-circuit the same guard on their own, so those reach the detector and the locator whatever this setting is — pre-existing, and unchanged either way by the documents check. Gating it matters because intake feeds the locator, and those rows are what `CountUserMessages` hands `isShortMsgFlood` — an unconditional guard would make one caption-less file or GIF the third strike under `--max-short-msg-count=3` for an operator who never enabled documents. With the check *on*, caption-less documents reach the detector and locator: they count toward `--max-short-msg-count`, and four identity-based checks run before the min-length gate (`detector.go:338`) and can each flag spam on their own: `isStopWord` (`detector.go:300`) matches against username and user ID as well as message text, so it can fire on an empty message; the meta-checks loop (`detector.go:309`) makes `UsernameSymbolsCheck` reachable, since it is message-independent; the Lua checks loop (`detector.go:314`) sees this message class; and CAS (`detector.go:324`) — enabled by default (`app/main.go:81`, `default:"https://api.cas.chat"`) — runs one lookup per such message and can permanently ban a CAS-listed user. Content checks find nothing in an empty message, and no LLM is reached at all: `DocumentsCheck` has already made `softSpam` true, so `Check` returns at `detector.go:355` ahead of the LLM block, whatever `--openai.check-short-messages` / `--gemini.check-short-messages` say, and neither provider's veto can override the verdict. Non-short cases proceed to the normal LLM path, where an enabled veto-mode provider can override the verdict. This includes a caption-less file whose appended parent brings `req.Msg` to at least `MinMsgLen`, or any caption-less file when `MinMsgLen` is 0
- `--meta.contact-only` and `--meta.audio-only` use the same intake gate: `TelegramListener.AdmitContacts` / `AdmitAudio` (wired from `settings.Meta.ContactOnly` / `Meta.AudiosOnly`) admit a text-less shared contact or audio file, otherwise `ContactCheck` and the "audio without text" branch of `AudioCheck` could never see the message they exist for. The three flags feed one `metaAdmitted` term in the guard, and the same locator/CAS trade applies
- No dedicated `--meta.document-text-len` knob. Threshold is `settings.MinMsgLen`, like `videos` and `audio`
- Not in `zeroAwarePaths`: a plain opt-in bool, default off, same as `Meta.Forward` and `Meta.ExternalReply`

### Contact Handling
- `ContactCheck` (`--meta.contact-only`) flags any message with `Meta.HasContact`. It used to flag only `HasContact && Msg == ""`, which a contact sent as a reply defeated: `bot.OnMessage` appends the replied-to text to `Msg`. A contact has no caption, so a contact never has authored text and "contact without text" is every contact. It is a blunt rule for not-yet-approved members; with `--paranoid` it hits established members too (README says so)
- The card's content (name, phone, vCard) is deliberately NOT folded into `message.Text`, unlike checklist and poll. Folding was tried and rejected in review: the phone, email and address of the sender or a third party would reach the locator, logs, spam log, admin chat, spam samples and LLM providers; ungated contacts would feed the duplicate detector (which bans approved members), `--max-short-msg-count` and the unvetoable prohibited-langs check (a contact's name is written by whoever saved it); and vCard 2.1 from Android needs quoted-printable/base64 decoding. Contacts stay behind the `AdmitContacts` intake gate, admitted only with `--meta.contact-only` on

### Prohibited Languages Detection
- `--prohibited-langs` (Settings.ProhibitedLangs, comma-separated) blocks messages written in an admin-configured set of Unicode scripts; solves English-only or single-script chats getting spam in another script (Chinese observed). Disabled by default (empty list)
- The check is an internal method `(d *Detector) isProhibitedLang(msg string)` (`lib/tgspam/detector.go:1186`) called inline in `Detector.Check` right after the short-msg-flood block and before the stop-words block (`detector.go:282-288`), gated by `len(d.ProhibitedScripts) > 0 && d.ProhibitedLangsMin > 0` so both an empty script list and a zero min (treated as disabled) do no work
- Hard return like short-msg-flood: on a hit it appends the response, `d.spamHistory.Push(req)`, and `return true, cr`, bypassing the LLM (policy rule the LLM can't override); a confirmed foreign-script message cannot be vetoed
- Unlike `isShortMsgFlood` it does NOT bail on `req.CheckOnly` and takes `msg string` rather than the full request: this is a pure content check, so the web `/check` UI must exercise it
- `Check` passes `req.AuthoredText()` (the user's own text), NOT the concatenated `req.Msg`, so quoted/reply-to content the user did not write cannot drive this hard, LLM-unvetoable permanent ban; the softer content checks below still see the full `req.Msg`. `AuthoredText()` strips the trailing `"\n"+Quote` from `Msg` when `Request.Quote` is set (populated by `bot.OnMessage`) and returns `Msg` unchanged when `Quote` is empty, so API/library callers that set only `Msg` are unaffected
- Counts letters only: walks runes, skips `!unicode.IsLetter(r)`, tests each letter against the configured script tables via `unicode.Is`, increments per-script counts, and returns spam the moment any single script reaches `ProhibitedLangsMin`. Digits, punctuation, emoji, and spaces do not count
- Deterministic reporting: `scriptNames` is sorted (`sort.Strings`) for stable tie-breaking and a stable `Details` string; the flagged response uses `Details: "<script>: <count>"` (e.g. `"Han: 3"`), the non-flagged response reports `"<script>: <count>/<min>"`
- Scope by placement: with default `FirstMessageOnly=true` the approval gate short-circuits earlier, so this runs only for non-approved users; in `--paranoid` mode or with `FirstMessageOnly=false` it also runs for approved users, same as every other content check. No `MinMsgLen` gate (short foreign spam is the target)
- `ResolveProhibitedScripts(names []string) (map[string]*unicode.RangeTable, error)` lives in `lib/tgspam/prohibited.go:29` (exported for cross-package use) and is the underlying resolver used directly by `makeDetector` (`app/main.go:768`, error already caught by validation so it discards it). It expands friendly aliases via `scriptAliases` (chinese→Han, russian/ukrainian→Cyrillic, japanese→Hiragana+Katakana, arabic, korean→Hangul, hebrew, thai, greek), matches other names case-insensitively against `unicode.Scripts`, skips empty/whitespace entries, and errors naming an unknown entry
- Validation goes through `ValidateProhibitedLangs(langs string, minCount int) error` (`lib/tgspam/prohibited.go:64`), which resolves the names and requires `min >= 1` when the list is non-empty. It is called from `Settings.Validate()` (`app/config/settings.go:276`), the single validator invoked at startup (`app/main.go:360`), by `save-config` (`app/main.go:393`), and at the web settings save boundary (`app/webapi/config.go:158`, rolls back the in-memory mutation on failure); this keeps a bad script name (or any other invalid settings combination) from being persisted and bricking the next `--confdb` startup
- `Config` fields: `ProhibitedScripts map[string]*unicode.RangeTable` (script name → range table, set directly from the resolver) and `ProhibitedLangsMin int` (`detector.go:128-133`). The map, not a slice, so the check can report which script hit and the resolver output is settable cross-package from `app`
- Two config knobs: `--prohibited-langs` / `PROHIBITED_LANGS` (empty disables) and `--prohibited-langs-min` / `PROHIBITED_LANGS_MIN` (default 3). Validation requires `min >= 1` when the list is non-empty
- `Settings.ProhibitedLangs` is in `zeroAwarePaths` (empty=disabled must survive merges, `config/settings.go:325`); `ProhibitedLangsMin` is NOT (default 3, zero is not a meaningful "disabled")

### No-Message Ban Notifications
- Bans without an underlying message (reaction spammers from `procReaction`, members flagged on join from `procJoin`, both in `app/events/listener.go`) are reported via `admin.ReportUserBan(banUserStr, user, cause)`, which reuses the same `change ban`/`info` inline keyboard as `ReportBan` (`sendWithUnbanMarkup`) so admins can unban+approve a wrongly banned user. The cause follows the user link on the first line: `reaction spammer` or `on join by lua-<name>[, lua-<name>]`
- The user link label goes through `markdownV1LinkLabel`, shared with `reportedUserMD`. Legacy markdown (`ModeMarkdown`) copies a label verbatim up to the first `]` and applies no escapes inside it, so `\]` cannot keep a `]` in the label and `escapeMarkDownV1Text` there shows its backslashes as text. The helper removes `]` and escapes nothing else. On the join path `banUserStr` falls back to the member's display name, and a `]` left in it would end the label early and let the name inject its own link into the admin chat
- The first line depends on the mode: `[training] would have permanently banned`, `[dry run] would have permanently banned`, `restricted` (soft-ban), otherwise `permanently banned`
- There is no message, so the callback carries `msgID = 0` as a sentinel. Two paths must honor it: `deleteAndBan` skips the Telegram delete when `msgID == 0` (removing the `if msgID != 0` guard would make every such confirmation try to delete message 0), and `callbackUnbanConfirmed` already discards msgID (`userID, _, err := parseCallbackData(...)`)
- The notification text keeps the `[user](tg://user?id=N)` link immediately after "permanently banned" or "restricted" because Telegram strips markdown from callback text; `extractUsername`'s plain pattern `(?:permanently banned|restricted) (.+?) \(-?\d+\)` would otherwise capture any words placed between them and the trailing `(id)` as the approved-user name
- The notification body is empty, so `getCleanMessage` returns an error or an empty string and the `cleanMsg != ""` guard makes unban skip `UpdateHam` and ban confirmation skip `UpdateSpam` — no `[reaction spam]` or name text is learned

### Lua Join Check
- A Lua plugin may define an optional `check_join(req)` next to the required `check`. `req` has only `user_id`, `user_name`, `first_name`, `last_name`, `is_premium`; the return values are spam and details, a third one is ignored. No settings: defining the function in an enabled plugin is the switch
- All scripts share one Lua VM. `LoadScript` sets the global `check_join` to nil before running a file in the main VM and then registers or deletes the script's entry in `Checker.joinCheckers`, so a script without the function cannot inherit the previous script's one. Reload goes through `LoadScript`; a failed load keeps the previous registrations, as for `check`. The registry holds each script's function value, so the platform always calls the right one, but a script body that calls `check_join` by global name gets whatever the last loaded script left (README tells plugin authors to share logic through a `local function`)
- `plugin.JoinCheck` returns `(Response, bool)`, false when the script has no `check_join` at call time; the function is looked up by name on every call. `GetJoinCheck`/`GetAllJoinChecks` are not on the exported `LuaPluginEngine`; the detector reaches them through the unexported optional interface `luaJoinEngine`, like `luaResultEngine`, and fills `luaJoinChecks` from the same plugin list as `luaChecks`
- `Detector.CheckJoin` runs only the join checks: spam when one reports spam without an error; no fallback to `check` or any other check, no approved-user, history or LLM changes. A Lua error never bans
- `SpamFilter.OnJoin` skips approved users (unban approves, so a wrongly banned user is not banned again on rejoin). `procJoin` runs at the top of the `NewChatMembers` branch in `Do`, before the `DeleteJoinMessages` fork, only for `l.chatID`, for every member (not the service message sender). It skips the bot itself (`l.BotUsername != ""` guard, otherwise every member without a username would match) and superusers, then mirrors `procReaction`: `Locator.AddSpam`, `SpamLogger.Save` with `[join spam]`, `banUserOrChannel`, `ReportUserBan`. An error for one member does not stop the others or the join message cleanup
- `joinBanCause` sorts plugin names: with an empty enabled list `luaJoinChecks` comes from a map, so the order is random

### Join Captcha
- `--captcha.enabled` (Settings.Captcha: `Enabled`, `Timeout` 10s..24h and `Message` checked by `Settings.Validate`: non-empty and within telegram's 1024 UTF-16 caption limit with `{user}` counted as a 129-char name) lives in `app/events/captcha.go`. The listener creates it in `Do` only outside training and dry modes; `l.captcha == nil` means disabled everywhere, and a press on a left-over captcha is still answered (`procCaptchaCallback`), otherwise the client spins
- `procJoin` calls `startCaptcha` for a member the Lua join check did not flag. Skipped: bots, approved users, members added by a superuser (service message `From` is a superuser and not the member); the bot itself and superusers are skipped earlier by `procJoin`
- `Start` makes no API call: it registers the pending entry (`msgID 0`, no timer) and hands the rest to `verify` on a worker goroutine limited by `captchaWorkers`. The update loop never waits on the status read, mute, render or upload, and `dropUnverified` deletes the member's messages from the moment of the join
- `verify` order matters. The failure cooldown is checked first: a member still in it is banned for the rest with no API status read and no render. Then `getChatMember` (through `Request`, no new `TbAPI` method): `restricted` by anyone but the captcha keeps its restriction (muting would replace a soft ban or admin mute with one that expires, and solving would lift it); `administrator`, `creator`, `left`, `kicked` are skipped; a status error verifies anyway. The captcha's own mute also reads as `restricted`, so it is recorded in `muted` (user → expiry) and told apart; checking status before the cooldown, or not recording the own mute, lets a member leave and rejoin under the mute and skip both. Then the mute (all permissions false, `timeout + captchaGrace (1m)`, expiring on its own so a lost captcha never mutes for good), then render and send, and only then the timer: a member queued for a worker can't time out before seeing the challenge. `isCurrent` checks between steps stop work for a captcha replaced, canceled or stopped meanwhile, and a post that finds its entry gone deletes what it sent. A render or send failure unmutes
- Unmute passes true for every permission with `UseIndependentChatPermissions`, which the Bot API documents as lifting a restriction: the member becomes a regular member bound by the chat defaults. Copying the chat defaults instead would keep a restriction and, with dependent permissions, could imply more than the defaults
- The challenge is `renderMotionCaptcha` (`captcha_image.go`): a black and white noise GIF where noise inside the digit mask scrolls down and outside scrolls up. Both noise fields are independent and `h+frames` rows tall, never periodic: a periodic texture would let a single frame reveal the mask boundary by comparing rows one period apart. Every frame and the frame average are uniform noise; only motion carries the digits. A frame-difference program defeats it (documented in README), general-purpose vision models looking at frames do not. the style (see below) is meant to survive telegram's GIF to H.264 conversion
- Answer: a `captchaCodeLen` (2) digit code and `captchaChoices` (6) candidate buttons, three per row, callback data `C<userID>:<candidate>` (`captchaPrefix`, routed in `Do` before the `R` report prefix; admin callbacks use `?`, `+`, `!` or none). `captchaCandidates` adds random decoys independent of the code. Decoys derived from the code (swapped digits, a digit ±1) were tried and rejected in review: the code becomes the per-position majority and the one candidate one step from all others, so a bot reads it off the keyboard. The first press decides, a guess passes 1 in 6, the doubling cooldown keeps repeated guessing slow. A keypad with a 3-digit code (1/1000) was the earlier design; it was harder to read and slower to answer
- Texts the bot shows members itself (callback answers, test results, "captcha is disabled") come from `captchaTexts` by the presser's telegram `language_code` (`captchaText`, "zh-hans" → "zh", english fallback). Join captcha answers take it from the callback's `From`; a test stores it on the entry (`lang`) since its result may be sent by the timeout. The caption stays `--captcha.message`, one per group. A new language needs every `txt*` entry, `TestCaptchaText` checks the lengths
- Style: `captchaStyle()` in `captcha_image.go` (6px blocks, 6-block strokes, 30 frames at 12.5 fps) was picked by comparing variants in real Telegram clients; it is a function returning a value, not a mutable global, since workers render concurrently. `renderMotion` takes any `motionStyle`
- Failures (wrong code, timeout, leaving with a pending captcha) are counted per user in memory. Wrong code and timeout call `remove`: `banUserOrChannel` until `now + cooldownFor(count)` (5m doubling to 24h), lifted by telegram itself; if the ban fails the member is muted for the cooldown instead, so a failure never leaves them free to post. Leaving records the failure without a ban. Entries older than `captchaMaxCooldown` are pruned on each failure; solving clears the user's entry. Soft-ban mode does not change this: the ban is temporary
- `HandleCallback` answers every press: other chats and stale message IDs (a rejoin replaces the pending entry and deletes the previous message, and a captcha not posted yet has ID 0) get the expired text (`txtExpired`), other users get their own text without touching state. `expire` takes the entry only if it is still the same pointer, so a solved, replaced or canceled captcha never bans
- `dropUnverified` runs in `Do` before the reply-command handlers and for edits, so a pending member's `/report` reply or edited message is deleted too. Accepted gap: a pending member posting "as channel" carries the channel's pseudo-user in `From`, which can't be tied to the member
- `Stop` (deferred in `Do`) stops the timers, waits for running verifications and deletes every pending captcha message; the mute expires by itself
- Turnstile mode (`captcha_turnstile.go`): a `--captcha.turnstile.site-key` switches `challenge` from the animation to a message with a telegram login_url button to `<url>/v/<nonce>` (`newNonce` = `crypto/rand.Text()`, 128 bits). `posted` registers the nonce in `nonces`; `take` and `register` (replace) drop it through `forgetNonce`, so a solved, expired, canceled or replaced captcha's page is gone (404). `ServeTurnstile` runs a separate server on `--captcha.turnstile.listen` with `turnstileRoutes`: both routes first pass `pageCaptcha`: the nonce must be posted and `telegramLogin` must verify the login_url data telegram appended (HMAC-SHA256 keyed with sha256(bot token) over the sorted `k=v` lines, auth_date within timeout+grace) for exactly `p.user.ID`. A plain URL button let anyone who tapped the group message pass for the member; login_url binds the page to the member's account, and needs @BotFather `/setdomain`. It does not bind who solves it: a link opened from the member's account carries valid login data and can be relayed to a human solver, same as any captcha. The widget's `data-cdata` is the nonce and siteverify must return it, so a Turnstile token solved on another page (another member's, or a fresh one) is refused. The form posts to the page url itself, so the login query rides along. `GET /v/{nonce}` renders the widget page, `POST /v/{nonce}` checks `cf-turnstile-response` with siteverify and `solveNonce` resolves it (join: clear failures, unmute; test: report). A page view resolves nothing. siteverify must report `success` AND the hostname of the public url: a token minted for another site using the same widget is rejected. A failed Turnstile re-renders the widget and keeps the captcha pending; only the timeout bans
- The page server is public by design and separate from the web UI (basic auth or OIDC login). `remoteip` is not sent to siteverify: it would come from `CF-Connecting-IP`, forgeable by anyone reaching the port directly. `ListenTurnstile` binds before `Do` continues, so a bad or taken address fails startup instead of posting buttons to a dead page; a later `Serve` error reaches `Do` through `turnstileErr` and stops it for the supervisor to restart. `challenge` falls back to the animation, with the animation's default prompt (`motionPrompt`), when the login button is refused (domain not set): unmuting on a send failure would let every member in unverified. It reports whether it posted a page, and only then `posted` registers the code as a nonce; the fallback's 2-digit code must never become a page url. siteverify's hostname is compared case-insensitively with the url host; the url must have no path, query or fragment (`config.ValidateTurnstile`, shared by `WithTurnstile` and `Settings.Validate`; it rejects a trailing `?`/`#` and a port-only host too). `data-language` goes through `turnstileLang` (zh-cn, ru, en, else auto) Page hardening: CSP `default-src 'none'` with Turnstile allowed, a per-response script nonce for the one inline callback, `frame-ancestors 'none'`, no-store, no-referrer; `rest.Throttle`/`SizeLimit` on the router
- `WithTurnstile` also needs the bot token (passed from `settings.Telegram.Token`). `validateTurnstile` (`config/settings.go`) checks site key, secret, listen and the url. The secret is a credential wired like `CAS.Token`: `FieldTurnstileSecret` in `sensitiveFieldAccessors`, `cliCredentials`, `collectMaskedSecrets`, blanked in `getSettingsHandler`, not in the form. Empty `--captcha.message` selects the mode's default prompt (`defaultMotionMessage` / `defaultTurnstileMessage`); `validateCaptchaMessage` allows empty but not blank. A stored `--confdb` message equal to the old flag default maps to empty in `main.go` `captchaMessage` (TODO remove once rows are re-saved). `solved` (clear failures, unmute) is shared by the button and page paths; both drop the nonce (`forgetNonce`), so a stale page can't solve a later captcha of the same member. Test results use `txtTestTimeoutPage` in Turnstile mode, never the nonce
- The member's telegram `language_code` is kept on the entry (`Start(user, lang)`) for the default prompt (`txtPromptMotion`/`txtPromptTurnstile`), the button label and the page; the page falls back to `Accept-Language`. Telegram fills it on the update's sender, so `startCaptcha` takes `msg.From.LanguageCode` when the member joined by themselves, `NewChatMembers[i].LanguageCode` otherwise (an inviter's language is not the member's)
- A `BOT_DOMAIN_INVALID` refusal of the login button sets `turnstile.refused` (atomic): one ERROR, then the animation for every challenge until restart, no failing send per join. Other send errors fall back for that challenge only. `p.page` records what was posted, so test results (timeout number) and `forgetNonce` follow the actual challenge, not the configured mode
- The page server runs on a context derived in `Do` and cancelled by its defer, so it never outlives the listener. `WithTurnstile` keeps only `loginKey` = sha256(bot token), not the token. Pages without the widget get a static CSP with no script source and no nonce; `--captcha.turnstile.listen` defaults to loopback, Docker deployments set `:8081`
- `--captcha.timeout-action` (`Settings.Captcha.TimeoutAction`, `ban` default or `mute`, empty means ban; validated only with the captcha enabled; web form select `captchaTimeoutAction`, gated on key presence) switches only the timeout path. `mute`: `expire` records the failure without removal and calls `mute(user, 0)`, which sends `UntilDate` 0 (forever) with no permissions and records `muted[user]` 100 years ahead, so `isMutedByCaptcha` keeps telling the bot's own mute apart. The cooldown branch of `verify` re-mutes for good instead of banning; after the cooldown, a rejoin under that mute reads as `restricted` by the captcha and gets a new challenge, and solving unmutes. A wrong answer still bans (`fail(…, true)`). `muted` is in memory: after a restart the permanent mute looks like an admin's, the member gets no captcha and stays muted (README says so)
- The captcha does not approve the member; message checks apply afterwards as for anyone else
- `/captcha` (or `/captcha@<bot>`) sent in a private chat by a superuser starts `StartTest` through `procCaptchaTest`, called from the private branch of `procEvents` and, first, from the admin-chat branch of `Do` (the admin chat may be the superuser's private chat, whose messages never reach `procEvents`). Edits are ignored (`EditDate != 0`), editing a message into the command must not start a test. The test is the join challenge with the join caption, posted in that private chat and kept in `tests`, not `pending`. No status read, mute, ban or failure count; `finishTest`/`expireTest` reply with the result and the number. `HandleCallback` picks the map by the press's chat: the primary chat → `pending`, the presser's own private chat → `tests`, anything else expired, so a test press can never solve or fail a join captcha. `register`, `posted`, `take`, `isCurrent` and `newCaptchaCode` serve both maps; `postTest` skips a test replaced before it got a worker and reports a send failure only for a test still current. Superusers only, because each test costs an upload, and in the animation mode a render; with the captcha disabled the bot says so
- `captcha.render` is injectable so timer tests are not slowed by GIF encoding under `-race`. `deleteMessage` and `answerCallback` in `events.go` are shared with the listener; `deleteMessage(…, 0, …)` is a no-op

### Web UI OIDC Login
- `--server.oidc.issuer` (`Settings.Transient.OIDC`) replaces basic auth for every webapi route, API included; no basic auth fallback, by the operator's choice. The settings are process-only (`json:"-"`, filled by `oidcSettings(opts)` in both `optToSettings` and the `--confdb` transient block in `main.go`): a stored login could lock the operator out of the page that edits it, an issuer overlaid from the CLI would be saved by the next UI save without its secret, and reload would show DB values while the startup login stays in force. Leaving the flags off is the recovery. `activateServer` drops the auth hash and `applyAutoAuthFallback` skips when `Transient.OIDC.Enabled()`
- Routing: `Run` registers `GET /auth/login`, `GET /auth/callback` and `POST /logout` on the root bundle and passes `s.routes` a `router.Group()` with `oidcAuth.middleware`. Do not exempt paths inside the middleware instead: `r.URL.Path` is decoded while ServeMux matches the escaped path, so `/auth%2Flogin` passed a string check and reached the catch-all `GET /` page without a session. Any other method on the login paths (e.g. `GET /logout`) lands in the guarded group
- `app/webapi/oidc.go`: authorization code with PKCE S256 via `coreos/go-oidc` + `x/oauth2`. Cookies are `base64url(json).base64url(blake3-keyed(purpose \x00 payload))` (`lukechampine.com/blake3`, 32-byte key) with a startup key from `crypto/rand`; the purpose (`session`/`state`) keeps a login cookie from verifying as a session, which it otherwise did since both decode into overlapping fields. A session also needs a non-empty `ID` and `Sub`, and holds nothing else (the callback checks `Sub` before the allow list). All cookies are HttpOnly, Secure (unconditional, the url must be https), SameSite=Lax
- Login: state, nonce, verifier and the return path ride in `tgspam_oidc_<state>` (path `/auth/`, 10m), one per login so tabs don't clash; `dropOldStates` keeps the newest two plus the new one, since abandoned logins would grow the request headers past proxy limits. The callback finds the cookie by the `state` query and still compares the signed state. `localPath` returns the `path.Clean`ed escaped path, since `http.Redirect` cleans too: a raw check let `/./\host` become `/\host`, which browsers read as `//host`; backslashes, literal or `%5C`, are refused
- `redirectToPublicHost` (middleware and login) sends a request for any host other than `--server.oidc.url`'s to it (GET/HEAD 302, HTMX `HX-Redirect`, others 421; host taken from `X-Forwarded-Host` when a proxy rewrites Host, compared lower-case without `:443`, parsed once in `newOIDCAuth`): the login cookies are host-bound and the provider calls back on the public url only, so a login started on a tailnet address could never finish
- Unauthenticated: a GET is redirected to `/auth/login?rd=<uri>`, an HTMX request gets 401 + `HX-Redirect` with `rd` from `HX-Current-URL` (the page, not the fragment), anything else 401
- Logout is `POST /logout` so `CrossOriginProtection` covers it; the navbar uses `hx-post`, answered with `HX-Redirect` to `end_session_endpoint?client_id=` (no `id_token_hint`: the session outlives the id token, and Rauthy rejects an expired hint; Rauthy ignores `client_id` and shows its own confirmation, Okta/Keycloak want it). A provider without that endpoint ends on `GET /auth/logged-out`, a static page outside the guard, because "/" would sign straight back in. `GET /logout` (bookmarks, cached pages; TODO-marked for removal) is a static page with a POST form, outside the guard too. Both pages send `default-src 'none'; frame-ancestors 'none'` and deliberately no `form-action`: browsers apply it to the redirects after a submit, so `'self'` would block the logout form's 303 to the provider since an XHR following a cross-origin 302 is blocked by CORS. It adds the session `ID` to `revoked` until the session's expiry (pruned on each logout). The allow list is checked at login only; revocation covers logout, not accounts removed later (documented, restart ends all sessions). Basic auth mode keeps `GET /logout` with a TODO next to the POST
- `discover` is lazy so the UI starts while the issuer is down. `fetchMu` serializes fetches so waiters share one; the fetch runs on `context.WithoutCancel` of the first request, so a client going away can't fail it for everyone, and a failure is cached for `oidcRetryAfter` (5s), so anonymous `/auth/login` or `/logout` floods cost one outbound request per interval. Login, callback and logout call `extendWriteDeadline` (45s): the server's 5s `WriteTimeout` is shorter than discovery + code exchange + JWKS on a cold provider
- The allow list (`role:`, `group:`, `email:` with `email_verified`, `sub:`) is matched against id token claims; `ValidateOIDC` refuses an empty list, since it would admit every account of the issuer, and requires an https issuer and `--server.oidc.url` as a bare https host (`isBareHTTPSURL`, shared with `ValidateTurnstile`). Only `group:` entries add the non-standard `groups` scope. `oidcAllow` trims entries (`"a, b"` in the env var) and drops empty ones before validation. `flexBool`/`stringList` accept `email_verified` as a string and a lone role or group as a string
- The client secret goes through `collectMaskedSecrets`; it is not in `sensitiveFieldAccessors`, `cliCredentials` or `getSettingsHandler` because it is never stored or serialized. The "Web Login" row on the settings page shows issuer, client and allow list read-only

### Jev Provider

- `--jev.token` / `JEV_TOKEN` enables jev (typesafe.ai), a decision model rather than a generator: one POST carries a `state` plus typed questions and each answer returns a number. `lib/tgspam/jev.go` asks one `noul` spam question (plus the optional `gibberish` noul below) and thresholds the returned probability in `verdict`, so `llm.go` and the `llmResponse{IsSpam, Reason, Confidence}` contract are untouched and jev inherits retry, history flattening and `Details` formatting unchanged
- Reuses the existing `HTTPClient` interface (`detector.go:185`) rather than defining a client interface of its own. `openAIClient`/`geminiClient` exist because the vendor SDK types are unmockable, not as a convention; jev is plain HTTP, so tests assert the real request body. It gets its own `*http.Client` at startup, NOT `Config.HTTPClient`, which is built with `settings.CAS.Timeout` (`app/main.go`) and would impose a CAS deadline on LLM calls
- `newJevChecker` returns `(*jevChecker, error)` and `WithJevChecker` returns `error`, assigning only on success (`WithLuaEngine` is the precedent for an error-returning `With*`). It validates rather than normalizing: finite `Threshold` in (0, 1], non-negative `MaxSymbolsRequest`, non-empty question and both criteria. Only `APIBase`, `Model`, `MaxSymbolsRequest` and `RetryCount` fall back to a default when unset; a zero `Threshold` and an empty question or criteria are REJECTED, not defaulted. Stating this as a blanket "zero takes the default" is what produced the original bug, where the constructor defaulted a zero threshold the contract said to refuse. `Settings.Validate()` enforces the identical contract on the same `IsJevEnabled()` predicate the startup wiring uses, so a config accepted at save time cannot fail to construct at next startup
- The probability decodes into a `*float64`. A plain `float64` leaves a missing key and an explicit `null` at 0.0, which is in range and would become a confident ham verdict that clears heuristic spam in veto mode. `Confidence` is direction-aware for the same reason: `p*100` for spam, `(1-p)*100` for ham
- NaN needs its own guard everywhere `Threshold` is validated. `strconv.ParseFloat` accepts `"NaN"` and a `t <= 0 || t > 1` test does not reject it, while every `p >= NaN` is false, so a NaN threshold makes jev return a ham verdict for every message. What that verdict then does depends on eligibility and `--llm.consensus`
- `IsJevEnabled()` is token-only, unlike `IsOpenAIEnabled()`'s token-or-apibase form, and `--jev.apibase` deliberately carries no `default:` tag. With a default the field is never empty, so an apibase-aware predicate would report jev enabled on every startup. `APIBase` is not validated at construction: a malformed endpoint surfaces as an ordinary check error, not a startup failure
- **Adding an LLM provider takes more than the `llmChecks` slice.** The short-message gate (`detector.go:343-352`) names its providers as separate locals and returns early only when none of them short-checks, so a provider registered only in the slice misses short messages exactly when no existing provider already opens that gate, and runs on them when one does. That configuration dependence is what makes the omission hard to spot. `llmResults` is also preallocated at the provider count, which is housekeeping rather than correctness
- The question and criteria defaults are `default:` struct tags, not constructor fallbacks: `defaultSettingsTemplate` (`app/settings.go`) fills by reflection over the tags and then runs `optToSettings`, so a constructor-only default never reaches `Validate()` and a token-only startup would fail its own empty-question check. `TestJevFrozenPolicyDefaultsMatchAppendix` asserts the tag values still equal the text recorded in the plan
- **The default threshold is a development candidate, not a validated default.** 0.30 was chosen on the same 150 production messages it was measured on, and that evaluation joined a post to its quoted text with a newline while `cleanText` fuses them (see `docs/backlog/cleantext-deletes-quote-separator.md`). Validating it needs fresh intake through the real cleaned input, with acceptance criteria frozen before scores are seen
- An errored provider result carries `flip=false`, which is the inherited consensus policy and not a rule of jev's own: under `any` a working provider can still flip the base decision in either direction, including clearing base spam in veto mode
- `--jev.gibberish-threshold` (0 = off, in `zeroAwarePaths`) adds a second noul, `gibberish`, to the same request; at or above the threshold it returns spam with its own reason and confidence, otherwise the spam question's verdict stands unchanged, and with it off the request body is the one-question form (`TestJevChecker_RequestShape` pins it with `JSONEq`). Its question and criteria are constants in `jev.go`, not flags: they are the wording the 0.50 recommendation was measured with (of 1,061 distinct 15+ character inputs rebuilt from six days of prod updates, only the target crossed it, next highest 0.31; wrong-layout and slang evidence comes from hand-written controls, peak 0.31; Cyrillic mash scores 0.32-0.37 and is missed). `Settings.Validate` rejects it with `Jev.HistorySize > 0`, because history is flattened into the judged `message` and an uncaught gibberish post in ham history would reach every later request, an untested combination. A missing or malformed `gibberish` answer is an error, never 0, same as the spam answer. The question is not asked when `req.Quote` is set (the jev closure in `Detector.Check` passes `req.Quote == ""` to `jevChecker.check`): `bot.OnMessage` appends quote or reply text to `Msg` and `cleanText` fuses it, so a caption-less reply to a gibberish post would otherwise be judged as pure gibberish and banned. `Quote` is set only when there is quoted or replied-to text, so a reply to a textless photo or sticker is still judged. When Jev runs, it still asks the spam question on messages with quoted or replied-to text; a gibberish post with quoted or replied-to text is an accepted miss

### LLM Checker Structure
- Shared provider-agnostic LLM flow lives in `lib/tgspam/llm.go`
- Keep provider-specific transport and request construction in `lib/tgspam/openai.go`, `lib/tgspam/gemini.go`, etc
- Common behavior such as history formatting, retry handling, and response detail formatting should be implemented once in `llm.go` to avoid `dupl` violations
- Shared behavior belongs in `lib/tgspam/llm_test.go`; provider tests should focus on API-specific behavior such as request shape, model options, truncation, and safety settings
- `context.Context` is threaded from `Detector.collectLLMCheck` → `check()` → `runLLMProviderCheck` → `sendRequest()` → API call; the detector creates a per-request context with `LLMRequestTimeout` (default 30s)
